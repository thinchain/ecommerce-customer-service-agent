# 项目说明与面试论证

本项目定位：可复现的电商客服 Agent 工程样本。已实现数据管线、多 Agent、RAG、MCP、评测、容器配置、限流熔断和监控。它不是已经服务真实用户的生产电商系统，不能把合成交易、规则测试或检索成绩描述成线上业务成绩。

## 1. 为何用 LangGraph，而不是手写框架？LangChain 用在哪里？

项目直接使用 LangGraph 的 StateGraph、条件边、子图、异步执行与递归限制，langchain-core 是其依赖；模型调用保留 OpenAI 兼容 SDK。**没有直接采用完整 LangChain Agent API，不应在简历中声称使用了未实现的组件。**

最初短小的 ReAct 循环用普通 Python 足够。现在有协调与三个专业子图、证据交接、决策入口、末尾校验、独立预算和错误传播，手写状态机需要自己维护调度、生命周期与图观察接口。LangGraph 统一这些执行机制，让工程代码聚焦数据权限、业务工具、证据和预算。不是“框架让模型更聪明”，也不是“所有工作都不需自己写”。

取舍：增加依赖、版本约束及节点边界调试成本；针对本地 vLLM 已有 SDK 无需再包一层 ChatOpenAI。MCP、数据库和检索保持框架外服务，未来可接别的编排器。当前未启用 checkpointer；若引入持久执行，还需 run_id、恢复 API、版本迁移、幂等动作，不能仅加一行 compile(checkpointer=...) 就声称容灾完成。

参考：[LangGraph 图与条件边](https://reference.langchain.com/python/langgraph/graph/state/StateGraph/add_conditional_edges)、[持久化接口](https://reference.langchain.com/python/langgraph.checkpoint)。

## 2. 为何这样拆 Agent？如何配合？

按数据源和权限边界拆分，不按“多几个角色看起来复杂”拆分：

| 角色 | 责任 | 数据与权限 | 拆分理由 |
| --- | --- | --- | --- |
| 协调 | 理解任务、委派、汇总、显式偏好记忆 | 历史摘要；无直接业务查询权限 | 保留跨领域上下文并控制预算 |
| 订单 | 订单、支付、物流、退款记录 | 当前沙盒用户的参数化 SQL | 内部动态事实不能被网页或 RAG 替代 |
| 商品 | 商品知识、政策、价格库存筛选 | RAG + 商品 SQL | 语义知识与结构化约束需要联合查询 |
| 资讯 | 外部公开时效信息 | DDGS；不自动接收历史或业务记录 | 隔离不可信网页和外部发送边界 |

典型依赖链：订单 Agent 查询订单 → 返回实际 product_id 和原始 observation → 商品 Agent 按 ID 检索兼容性 → 协调 Agent 合并物流与知识证据 → 校验引用 ID。交接既有报告也有工具证据，避免多 Agent 逐层复述放大幻觉。

角色共享一个本地模型，拥有不同提示词、工具白名单与上下文；并非部署四份 GPU 模型。当前串行执行是因为依赖关系和单并发推理资源。独立任务可在未来用 fan-out 并行，但先要评测排队、延迟和预算。普通聊天不委派，简单查询通常只唤起一个专业角色。没有证据表明多 Agent 必然比单 Agent 准确；它首先提供职责/权限边界。

## 3. 怎么评价项目好坏？

不要只报一个“准确率”。以下指标分别覆盖链路：

| 层次 | 指标与标签来源 | 当前实现 |
| --- | --- | --- |
| 业务数据 | 外键错误、订单合计差、退款超付、未来签收日期 | 全库 SQL 审计 |
| 检索 | Hit@4、Recall@4、MRR@4、nDCG@4、无答案空结果率 | 660 条版本化合成查询，按商品 ID 分 dev/test |
| 路由/工具 | 专业 Agent 集合精确匹配、必须工具、禁止工具 | 真实 API 验收脚本和标注样例 |
| 最终答案 | 业务事实断言、错误承诺、引用 ID 有效性 | 规则验收；引用校验不是语义事实核验 |
| 语义质量 | 有依据性、完整性、拒答适当性 | 需人工盲评及双人争议仲裁；尚未测量 |
| 效率/可靠性 | 延迟 P50/P95/P99、吞吐、429比例、5xx、token、工具失败率 | Prometheus + 两类独立 Locust 场景 |

检索实验必须解释条件：测试集按 product_id 分组，查询针对合成规格；公开 PQA 是索引的一部分，但本次相关性标签不覆盖其真实问答准确性。已知商品过滤相当于实体定位正确的条件检索，不代表 Agent 在自然语言中总能定位对商品。未过滤检索是消融对照，不能夸大为整体客服提升。测试集不用于调整阈值；在 dev 上调参，test 只用于锁定版本后的评估。

真实回答验收：先启动模型/API，再运行 scripts/evaluate_agent.py。HTTP错误保留在分母，不只挑成功请求。10条用例是验收起点，不足以对外宣称总体准确率；下一阶段应收集至少200条经人工标注的真实风格问题，覆盖单领域、复合、歧义、无答案、攻击、失败后重试，报告样本分布和置信区间。为比较多 Agent 的准确率收益，还需要在同模型、同工具、同token预算下增加单 Agent 基线；本项目尚无这一成绩。

## 4. Jev 应放在哪里？

这里的 Jev 是 TypeSafe AI 的决策模型，不是 Judge–Executor–Verifier 缩写。根据[官方 API](https://docs.typesafe.ai/api)，它接收 state 和类型化问题，支持 Choice、Score、Noul。Choice/Score 的 confidence 来自概率分布形状，不能当成“实际业务准确率”，阈值必须在本项目标注数据上校准。[官方 confidence 说明](https://docs.typesafe.ai/confidence)

| 决策位置 | 可选机制 | 工程处理 |
| --- | --- | --- |
| 入口意图/领域 | Choice：orders/product/research/mixed/chat/unclear | **已实现可选接口**，默认 off；shadow 只记录，advisory 高分给协调器建议 |
| RAG 候选筛选 | Score 或 Noul：片段是否回答当前问题 | 待实验，与 BM25/向量+reranker 基线比较召回损失与新增延迟 |
| 回答证据支持 | Noul：声明是否得到给定片段支持 | 待实验；不能代替金额校验、引用查重或人工审核 |
| 复杂/模糊售后 | Choice：继续查证、询问、建议人工 | 待实验，动作空间白名单，低置信度拒绝自动决定 |
| 故障处置建议 | Choice：换知识源、澄清或交人工 | 仅辅助；超时、重试次数、预算仍由确定性代码控制 |

`JEV_MODE=off|shadow|advisory`，`JEV_API_KEY` 和 `JEV_MODEL` 可配置。实现使用 `/v1/systemone`，可通过 `JEV_BASE_URL` 选择本地 Kev 或云端 TypeSafe；本地端点不要求密钥，云端端点要求 `JEV_API_KEY`。默认不调用外部服务；开启后仅发送截断且做基础标识脱敏的当前问题，不发送整个会话、记忆、订单表。基础正则不是完整 DLP，真实部署需隐私评估。供应商超时/错误/低置信度时回到既有协调器，Jev 不能覆盖工具权限或直接批准退款。

已通过本地 Kev 接口冒烟测试，但未评估其中文分类质量、延迟分布或阈值收益；0.8 仅是保守实验阈值。先 shadow 记录与人工标签比较校准误差、错误接受率及覆盖率，再考虑硬路由。不能在简历中写“Jev 提升准确率 X%”。

## 5. 容灾、压测和真实业务边界

已落地：整体超时和执行预算、模型瞬态故障有限重试、熔断/单探针恢复、无等待队列的并发准入、429 Retry-After、SQLite WAL 会话与带 token 的租约隔离、错误不提交本轮记忆、局部 Agent 失败保留证据、liveness/readiness、Prometheus、请求关联 ID、在线快照校验与恢复工具、Compose 重启与持久卷。

本地进程级限流/熔断不能自动跨多个副本同步；Compose 默认一个 API worker。SQLite 单机备份不是跨机容灾，没有主从自动切换、跨可用区高可用或多副本负载均衡。模型宕机不能由自动重启 API 修复，也不应伪造回答降级。备份能恢复已提交会话，运行到一半的图不能恢复。

真实上线还缺认证与租户隔离（当前固定可信沙盒用户）、权限审计、隐私和保留期、共享限流、Postgres/托管数据库、异地备份与恢复演练、checkpoint 和事务动作幂等性。读工具可安全重试；退款/下单等写工具若加入，必须带业务幂等键、权限校验、明确确认与人工审批，不能复制当前读操作重试方式。

压测分别运行目录接口和 ChatUser：前者是 HTTP/SQL 基线；后者才含模型推理、Agent多轮、RAG/MCP。容量结论必须带模型版本、GPU、vLLM配置、并发、请求分布、延迟目标、持续时间。20秒 localhost 冒烟仅证明流程可跑，不是极限性能或稳定性测试。运行方案见 [部署运维](operations.md)。
