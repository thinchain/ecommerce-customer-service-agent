## 3. 完整 STAR 项目说明

### S — Situation：项目背景与问题

电商客服问题经常同时涉及商品知识和动态业务状态，例如“我的耳机还没到，它能连接 Windows 笔记本吗”。前者需要商品知识检索，后者需要本人订单与物流查询，价格和库存则必须来自结构化数据库。仅让模型生成回答，无法可靠提供这些事实；将全部历史和工具交给单一角色，也增加了上下文管理、权限控制和错误排查的难度。

在项目中，我希望把本地大模型能力接入完整应用链路，处理多领域查询、工具证据交接、失败恢复及效果验证，形成能够演示和复现的工程系统。

### T — Task：目标与个人责任

作为主要负责人，我负责整个项目的方案和架构设计，主导以下任务：

1. 建立 Web 界面、后端服务、本地推理、业务数据与知识库之间的调用链路。
2. 将订单和商品查询按职责与权限拆分，支持复合任务的依赖传递。
3. 统一模型、消息、配置、Agent 和工具接口，避免不同模块重复定义协议。
4. 建立可复现的数据、检索消融和回归测试体系，让结果有证据可查。
5. 在本地推理资源限制下控制执行成本与失败行为，保留会话与工具证据。

项目验收以功能链路、接口约束、测试和限定条件下的评测为依据，不把未上线的演示系统当作真实电商业务成果。

### A — Action：关键设计与实施

**行动一：按数据源与权限划分 Agent。**

使用 LangGraph 主图编排协调、订单和商品角色，专业角色内部使用有界 ReAct 子图。协调 Agent 负责拆解和汇总；订单 Agent 查询订单、支付、物流及退款记录；商品 Agent 结合知识检索和价格库存 SQL。每个角色拥有独立提示词、上下文和工具白名单，执行端再次检查工具权限。

对于有依赖的任务，先由订单 Agent 返回实际 `product_id`，再让商品 Agent 使用该 ID 检索知识；交接包含报告、原始 observation、失败状态和截断标识。角色共享本地模型服务，当前按需串行执行，避免为了展示协作而调用所有角色。

**行动二：让知识与业务事实使用各自的数据来源。**

建立商品、用户、订单、明细、支付、物流、退款和工单数据模型，使用固定 SQL 模板和参数绑定查询动态事实，金额使用整数分。工具不接受模型提供任意 SQL 或用户身份。商品功能、兼容性和政策进入知识库，价格库存和订单状态始终查业务库。

实现公开 PQA 导入、商品 ID 归一化、来源与许可元数据保留，以及分块、重叠和幂等更新。默认使用中文 bigram 与英文词项的 FTS5 / BM25 检索，支持商品与文档类型过滤；另提供 Chroma 与独立 Embedding 服务的可配置路径。实际检索成绩来自 FTS5 路径，不能描述为向量检索成绩。

**行动三：以统一契约连接 Agent、工具与会话。**

抽象 `Message`、`ConversationMessage`、`Settings`、`AgentConfig`、`Agent`、`RunContext`、`AgentResult` 和异步模型协议。模型消息校验角色以及 `tool_calls/tool_call_id` 的完整配对，序列化时移除内部元数据；会话记录保留执行轨迹，兼容缺少 ID 或时间戳的旧消息。

每轮显式传入历史与记忆，Agent 不持有共享 `_history`。通过 ContextVar 实现任务级配置覆盖，并将配置传递到线程及 MCP 子进程。业务参数模型同时用于生成 LLM 与 MCP schema，进程内与 stdio 两种传输复用校验和业务服务。

**行动四：控制证据缺口和历史误用。**

工具结果、检索片段和历史记录作为数据处理；商品任务核对必需查询是否取得有效结果，回答末尾校验引用 ID 是否来自实际证据。保存原始回答与执行记录，常规模型上下文按预算选取获准的原始问答对。

接入可配置的 Kev 客服范围分类与领域建议接口，区分新业务查询、历史回顾和范围外请求。历史回顾使用只读路径，明确区分历史价格与实时价格。引用 ID 校验不等于语义事实核验，分类器置信度也不等于客服准确率。

**行动五：让失败、取消和并发具有明确行为。**

设计协调轮数、专业轮数、委派次数、工具调用数和上下文预算，范围分类与执行共享整轮超时。模型连接或瞬态错误有限重试并加入退避、抖动与熔断；模型生成超时不自动重试，避免向共用推理服务堆积重复工作。

采用 SQLite WAL 和带 token 的会话租约，防止旧执行覆盖新执行。同一会话的并发写入被拒绝；全局准入饱和返回 429。专业 Agent 失败保留已取得证据，协调模型错误、取消或总超时不提交本轮历史与记忆。

**行动六：补齐交付与验证链路。**

接入本地 Qwen3.5-4B / vLLM，与 Kev 服务完成接口联调；Next.js 提供多轮问答、会话恢复、显式记忆管理以及工具和协作记录展示。提供健康检查、请求关联 ID、Prometheus 指标、Locust 场景、SQLite 在线备份与恢复校验，以及容器和 CI 配置。

以脚本化模型和模拟 HTTP 验证可控的边界行为，同时运行真实 LangGraph、MCP stdio 和 Chroma 存储测试。建立商品 ID 分组的检索保留集，使用同一索引进行带过滤和无过滤消融，分别报告检索、业务数据一致性和接口性能。

## 6. 常见追问与回答要点

- **为什么采用多 Agent？** 按数据源和权限分工，便于控制上下文和检查证据；没有证据表明增加角色必然提高回答准确率。普通任务按需处理，不固定调用全部角色。
- **为什么采用 LangGraph？** 当前有条件边、专业子图、循环、预算和错误传播，图编排便于组织执行；消息、工具、配置和 Agent 契约由自己定义。没有使用完整 LangChain Agent API。
- **RAG 使用什么检索？** 默认 FTS5 / BM25 词法检索；Chroma 是可配置的向量路径。报告中的检索数字来自 FTS5，同次请求没有实现词法与向量融合或 reranker。
- **108 项测试意味着什么？** 证明当前版本在已有用例中满足接口、权限、事务和失败行为约束；不能证明真实模型的总体任务完成率。
- **如何减少无依据回答？** 动态事实查 SQL、知识保留来源，工具返回原始证据，核对必要查询和引用 ID，历史值与当前值分开。没有做全面语义核验，不能承诺消除幻觉。
- **如何处理模型故障？** 对可重试瞬态故障做有限重试与熔断；生成超时不重复请求。专业角色失败保留证据，协调失败不提交本轮历史与记忆。
- **项目能否上线？** 当前是固定沙盒身份的本地系统，具备工程化基础；上线还需要真实认证、用户与租户授权、数据治理、共享限流及生产存储和部署验证。
